# Anamorphosis

**Anamorphosis** — мобильная 3D-головоломка на Unity, построенная вокруг механики совмещения тени 3D-объекта с заданным силуэтом.

Игрок меняет положение объекта и направление света, пока его проекция не совпадёт с целевой формой. Основная задача проекта заключалась не только в реализации механики, но и в построении архитектуры, которую можно расширять новыми уровнями, режимами и удалённым контентом без изменения основной игровой логики.

**Platform:** Android
**Engine:** Unity 6
**Render Pipeline:** URP
**Language:** C#

## Gameplay

Основной режим представляет собой последовательность 3D-головоломок.

На сцене находится абстрактный 3D-объект и источник света. Игрок вращает объект и подбирает его положение относительно света, чтобы получившаяся тень совпала с целевым силуэтом.

Когда положение достаточно близко к правильному:

* управление вращением блокируется;
* объект автоматически доводится до целевого положения;
* фиксируется результат;
* сохраняется время прохождения.

В проекте также реализован отдельный **Puzzle Mode**, в котором игрок работает с набором элементов, меняя их положение и ориентацию.

## Основные игровые системы

### Rotation Gameplay

Отвечает за основной игровой цикл уровня:

```text
Input
  ↓
GameplayInput
  ↓
Object Rotation / Light Rotation
  ↓
RotationTracker
  ↓
Target Reached
  ↓
Auto Snap
  ↓
Level Complete
```

`RotationTracker` не зависит от UI или конкретного способа ввода. Он отвечает только за определение того, насколько текущее состояние объекта соответствует целевому.

Это позволяет отдельно менять управление, визуальное представление прогресса и саму логику проверки.

### Progress

Во время прохождения отображается прогресс совпадения с целевым положением.

Для этого используется несколько состояний прогресса, которые заполняются по мере приближения объекта к целевой ориентации.

### Game Timer

Время прохождения уровня вынесено в отдельную систему.

Таймер учитывает состояние игры и не продолжает отсчёт во время паузы. После завершения уровня полученное время передаётся в систему сохранения результатов.

### Level Availability

Доступность уровней не хранится непосредственно в UI.

Отдельный сервис определяет:

* доступен ли уровень;
* выполнены ли условия его открытия;
* пройден ли предыдущий уровень;
* лучшее время прохождения.

UI только отображает результат работы этого сервиса.

Такой подход позволяет менять правила разблокировки без изменения интерфейса выбора уровней.

# Architecture

Проект использует **Dependency Injection через VContainer**.

Вместо глобальных синглтонов зависимости передаются объектам через контейнер. Это позволяет разделять инфраструктурные сервисы, UI и конкретный игровой режим.

Основные scopes:

```text
ProjectScope
│
├── MainMenuUIScope
│
├── RotationGameplayScope
│
└── GameplayPuzzleScope
```

`ProjectScope` содержит зависимости, которые нужны на протяжении всего приложения.

Gameplay scopes содержат зависимости, относящиеся только к конкретному режиму игры.

Это позволяет не загружать и не держать в памяти системы, которые не используются в текущем режиме.

## Scene Flow

Игровой уровень не является полностью самостоятельной сценой.

Environment Scene загружается **additively**, после чего игровой объект создаётся отдельно на основе конфигурации уровня.

Упрощённо поток выглядит так:

```text
LevelConfig
    │
    ├── Environment Scene
    ├── Gameplay Object
    ├── Level Sprite
    └── Level Type
            │
            ↓
      Gameplay Entry Point
            │
            ├── Load Environment
            ├── Spawn Gameplay Object
            ├── Initialize Gameplay
            └── Start Level
```

Такое разделение позволяет использовать одну и ту же игровую логику для разных окружений и наборов объектов.

# Data Driven Levels

Параметры уровня вынесены в конфигурацию `LevelConfig`.

Конфигурация содержит:

```text
LevelId
EnvironmentScene
GameplayObjectPrefab
Sprite
LevelType
```

`LevelType` определяет, какой gameplay flow должен использоваться.

Например:

```text
Rotation
RotationTutorial
Puzzle
PuzzleTutorial
```

Благодаря этому добавление нового уровня не требует создания отдельной игровой логики.

Чтобы добавить новый контент, достаточно создать конфигурацию и необходимые assets.

# Addressables

Для управления контентом используется **Unity Addressables**.

Это особенно важно для событийных уровней и дополнительного контента, который не обязательно должен находиться в основном приложении.

Общий сценарий:

```text
Main Build
    │
    ├── Core Gameplay
    ├── UI
    └── Base Content
             │
             ↓
       Addressables
             │
             ├── Event Levels
             ├── New Content
             └── Additional Assets
```

Удалённый контент загружается отдельно.

При невозможности получить remote content предусмотрен **локальный fallback**, поэтому базовая версия игры остаётся работоспособной без загрузки дополнительного контента.

Такое разделение также уменьшает связанность между основным gameplay и дополнительными наборами уровней.

# Input

Для обработки управления используется **Unity Input System**.

Логика ввода отделена от конкретных игровых систем.

`GameplayInput` преобразует пользовательские действия в игровые события, а gameplay-системы уже решают, что с этими событиями делать.

Это позволяет не связывать `RotationTracker`, таймер или UI непосредственно с Unity callbacks конкретных кнопок.

Для UI также реализована обработка состояний:

```text
Press
Hold
Release
Tap
```

Долгое нажатие используется отдельно от обычного tap, что позволяет реализовывать разные типы взаимодействия без дублирования UI-логики.

# Async Loading

Для асинхронных операций используется **UniTask**.

В основном это касается:

* загрузки сцен;
* загрузки Addressables;
* последовательности инициализации gameplay;
* ожидания завершения асинхронных операций.

Например, запуск уровня проходит последовательность:

```text
Load Scene
    ↓
Wait Until Ready
    ↓
Load Gameplay Asset
    ↓
Spawn
    ↓
Play Spawn Animation
    ↓
Start Timer
    ↓
Enable Input
```

Таким образом, игрок не получает доступ к gameplay до того, как необходимые зависимости действительно готовы.

---

# Animation & UI

Для tween-анимаций используется **DOTween**.

Он применяется для:

* появления объектов;
* переходов UI;
* анимаций меню;
* feedback при завершении уровня;
* плавного изменения отдельных параметров.

UI старается не содержать gameplay-логику.

Например, экран завершения уровня получает результат прохождения, но не занимается расчётом самого результата.

# Localization

Текст интерфейса подготовлен для локализации.

Tutorial text отображается с typewriter-эффектом, при этом сама система текста не зависит от конкретного gameplay режима.

Это позволяет переиспользовать tutorial-представление между разными уровнями.

# Puzzle Mode

В проекте присутствует отдельный режим головоломок с набором элементов.

Основные взаимодействия:

```text
Tap → Rotate Piece 90°

Hold Piece A
      +
Tap Piece B
      ↓
Swap Pieces
```

При этом логика состояния элементов отделена от их визуального представления.

Целевое состояние сравнивается с текущим состоянием набора, после чего определяется завершение головоломки.

# Event Content

Архитектура позволяет добавлять временные наборы контента без изменения основной системы уровней.

Например:

```text
Core Levels
    │
    ├── Rotation
    └── Puzzle

Event Content
    │
    ├── New Year
    ├── Summer
    └── Future Events
```

С точки зрения gameplay это остаётся тем же `LevelConfig`, но assets события могут приходить через Addressables.

Таким образом, система уровней не знает, является ли конкретный уровень обычным или событийным.

# Mobile Optimization

Проект ориентирован на мобильные устройства, поэтому производительность учитывалась на уровне архитектуры и контента.

Основные направления оптимизации:

### Rendering

Используется **URP** с учётом мобильной стоимости материалов и эффектов.

При работе с большим количеством одинаковых объектов применимы:

* GPU Instancing;
* SRP Batcher;
* Frustum Culling;
* LOD;
* минимизация лишних draw calls.

### Memory

Addressables используются не только для удобства загрузки, но и для контроля жизненного цикла ресурсов.

Нет необходимости держать весь дополнительный контент загруженным одновременно.

### CPU / GC

Отдельное внимание уделялось количеству создаваемых объектов и лишним аллокациям.

В часто вызываемых участках игровой логики предпочтительно избегать ненужных allocations и постоянного создания временных объектов.

### Physics

Для физических объектов важно разделять объекты, с которыми игрок действительно взаимодействует в текущий момент, и остальные.

Неактивные объекты не должны постоянно получать такой же объём физической обработки, как объекты в зоне взаимодействия.

# Why These Decisions

### VContainer вместо глобальных Singleton

Позволяет явно видеть зависимости и уменьшает связанность систем.

### ScriptableObject Configuration

Уровень описывается данными, а не отдельным набором hardcoded логики.

### Additive Scenes

Окружение и gameplay не обязаны существовать в одной сцене. Это упрощает переиспользование игровых систем.

### Addressables

Позволяют отделить базовый билд от дополнительного контента и обновлять наборы уровней независимо от core gameplay.

### Отдельные Gameplay Systems

`RotationTracker`, `GameTimer`, `GameplayInput`, `LevelAvailabilityService` и UI имеют разные зоны ответственности.

Изменение одной системы не должно приводить к переписыванию остальных.
